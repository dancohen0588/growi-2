● Growi · Spec produit · /dashboard

Une page d'accueil qui répond avant
que l'utilisateur ne pose la question.

Aujourd'hui /dashboard est un menu : 9 cartes vers les autres modules, des compteurs codés en dur à 0, aucune lecture Prisma. Cette proposition transforme la route en centre de décision quotidien : ce qu'il faut faire aujourd'hui, ce qui menace mes plantes, ce que la météo change, ce que je peux explorer ensuite — branché sur les données déjà disponibles (PlantInstance, getGardenAdvice(), Open-Meteo).

02Vision & 4 piliers

Le dashboard doit répondre à quatre questions dans l'ordre où elles se posent quand on ouvre l'app :

1

Que dois-je faire maintenant ?

Top 3 actions du jour (arroser, rentrer la basilic, semer les radis), tirées de getGardenAdvice(), validables en un clic via DoneButton déjà existant.

2

Qu'est-ce qui menace mon jardin ?

Alertes météo (gel, canicule, sécheresse) + état santé des plantes (healthStatus !== 'HEALTHY'). Bandeau dégradable selon sévérité.

3

Comment va mon jardin ?

3 KPIs vivants : nb de plantes, tâches semaine, alertes — chacun cliquable vers la vue détail correspondante. Sparkline 14 j sur l'arrosage (à partir de WateringLog).

4

Qu'est-ce que je peux explorer ?

Identifier en photo (hero), grille de modules, encart « plante à découvrir » (PlantCatalog au hasard / saisonnier), CTA Premium contextuel.

06Plan d'implémentation

Quatre phases, ~5–7 j-h frontend cumulés. Chaque phase laisse la branche dans un état déployable.

Phase 0 · 0,5 jPréparer le terrain (zéro régression)

Nettoyer le statique avant d'y poser du dynamique. Fin de phase : la page actuelle reste visible, mais débarrassée des chausse-trapes.

  1. Retirer les 2 FeatureCard qui pointent vers des routes inexistantes (/dashboard/diagnostic, /dashboard/marketplace) — ou créer des stubs page.tsx « Bientôt disponible » et garder les liens.app/dashboard/page.tsx:50,63
  2. Décision design : choix entre stubs ou retrait (recommandé : stubs, pour ne pas casser l'UX de découverte).décision
  3. Ajouter en haut de fichier un commentaire JSDoc résumant la composition (utile pour la maintenance).doc

Phase 1 · 1,5 jBrancher les stats & l'empty state

Premier signal de vie : les chiffres ne sont plus des « 0 » menteurs, et un nouvel utilisateur reçoit un parcours guidé. Pas encore de dépendance à l'advice engine.

  1. Créer lib/dashboard/loaders.ts exportant getDashboardOverview(userId) : retourne { garden, plantCount, plantCountThisMonth, hasOnboarded }.nouveau
  2. Composant StatRow (server) qui prend ces props et rend 3 tuiles cliquables (vers /dashboard/plantes, /dashboard/calendrier, /dashboard/calendrier?tab=alerts).components/dashboard/
  3. Composant EmptyStateOnboarding : 3 étapes (« Crée ton jardin → Ajoute ta première plante → Active les alertes »), CTA principal vers /dashboard/jardin.components/dashboard/
  4. Brancher dans page.tsx : si !hasOnboarded → render EmptyStateOnboarding + hero CTA Identifier + FeatureGrid (sans stats).app/dashboard/page.tsx
  5. Sinon → render StatRow avec données réelles.app/dashboard/page.tsx
  6. Test Playwright minimal : un utilisateur sans jardin voit l'empty state ; un utilisateur avec ≥1 plante voit les stats correctes.e2e/

Phase 2 · 2 jBrancher l'advice engine (briefing + actions + alertes)

Le dashboard devient utile : on voit ce qu'il faut faire et ce qui menace. Réutilise 100 % de l'engine déjà servant /calendrier.

  1. Étendre getDashboardOverview : appel à getGardenAdvice(garden.id, userId) (en parallèle du plantInstance.count avec Promise.all).lib/dashboard/loaders.ts
  2. Composant HeaderBriefing (server) : salutation + date FR + résumé météo (weather.current.temperature) + nb d'actions du jour. Skeleton si météo indispo.components/dashboard/
  3. Réutiliser WeatherAlertBanner existant (components/dashboard/calendrier/) — soit en l'important tel quel, soit en le déplaçant vers components/dashboard/shared/.refacto léger
  4. Composant TodayStrip = wrapper server qui filtre actions sur dueDate === today && !done, prend les 3 prioritaires (priority === 'high' en premier), et rend 3 ActionCardMedium (déjà existant).components/dashboard/
  5. Wrapper client TodayStripClient pour le bouton « Fait ✓ » : appelle la Server Action de toggle existante puis router.refresh().client component
  6. Gestion d'erreur : si getGardenAdvice throw (cas existant dans CalendrierPage), on log et on rend la page sans TodayStrip ni WeatherAlertBanner — pas de page blanche.try/catch
  7. Test Playwright : un jardin avec actions du jour affiche bien le strip ; cocher « Fait » fait disparaître l'action sans recharger la page complète.e2e/

Phase 3 · 1 jDécouverte & finitions

Tirer parti de l'écosystème (catalogue, Premium) et soigner le rendu pour livrer.

  1. Composant PlantOfTheMonth : sélection saisonnière (mai = pivoine / rose / lavande…). Fallback statique au début si le champ floweringMonths n'existe pas encore en BDD.components/dashboard/
  2. Élaguer la FeatureGrid à 6 cartes (retirer ce qui devient redondant avec le briefing : Météo + Calendrier déjà résumés en haut → conserver mais réordonner).app/dashboard/page.tsx
  3. Animations fadeUp staggered via lib/animations.ts sur les blocs principaux, en respectant useReducedMotion.lib/animations.ts
  4. Audit a11y : ordre de tabulation, contrastes, alt-text, aria-live="polite" sur le banner d'alerte.a11y
  5. Audit perf : tout reste RSC sauf TodayStripClient ; pas de fetch client redondant. Vérifier que le payload JS ajouté reste < 5 ko.vercel best practices
  6. Instrumentation (voir §08) avant merge.analytics

08KPIs & instrumentation

À mesurer dès la mise en ligne pour valider l'hypothèse « le dashboard devient une rampe d'action quotidienne ».

  • Taux de clic sur TodayStrip — % de sessions où ≥ 1 action est cochée depuis le dashboard (vs cochée depuis /calendrier).
  • Activation J+7 — % d'utilisateurs ayant cartographié leur jardin et ajouté ≥ 3 plantes (déjà au CLAUDE.md, à exposer ici).
  • Taux d'utilisation Identifier — % de sessions où la CTA hero est cliquée (probable baisse car le hero est plus bas qu'avant : à arbitrer).
  • Bounce sur empty state — % de nouveaux utilisateurs quittant la page sans cliquer aucune étape d'onboarding.
  • Latence p95 du loader — getDashboardOverview doit rester < 400 ms en cache chaud (cache GardenAdviceCache déjà en place).
